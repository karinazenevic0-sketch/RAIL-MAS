# МАС: железнодорожные перевозки грузов (JADE) — каркас

Каркас по схемам `1_etap1_dopustimyi_plan`, `2_etap2_rebalansirovka`, `3_otkaz_vagona`.
Нужны JDK 21+, `lib/jade.jar`, `lib/gson-2.13.1.jar`.

## Агенты
| Агент | Где | Роль |
|---|---|---|
| `CoordinatorAgent` | сервер | только ПОЛУЧАЕТ отчёты, проверяет допустимость, считает критерии, пишет `out/*.json`, `out/report.html` |
| `StationAgent` | сервер | окна погрузки/приёма (число путей), перенос и обмен окон |
| `LocomotiveAgent` | сервер | брони по интервалам, ограничение суммарной тяги, атомарный обмен броней |
| `WagonAgent` | клиент | **считает стоимость** (тариф + 0,75·порожний км + 25·часы опоздания), совместимость, очистка, временная блокировка интервала, бронь, обмен рейсов, отказ |
| `CargoAgent` | клиент | **сам знает** тип, вес, дедлайн; ищет вагон; на этапе 2 сам опрашивает ВСЕ грузы; при отказе сам ищет замену |

## Запуск
* Один компьютер: `run\local.bat` (`railway.LocalMain`).
* Два компьютера: ПК1 — `railway.ServerMain` + `ClientMain <IP ПК1> cargo pc1`;
  ПК2 — `ClientMain <IP ПК1> wagons pc2 <свой IP>`. Порядок любой: грузы стартуют, когда в DF видны все агенты.
* На обоих компьютерах одна версия кода и `data/input.json`.

## Незапланированные ситуации
* В `input.json`, секция `failures` (отказ вагона через `atMs` мс после старта).
* Вручную в консоли клиента «вагоны»: `fail wagon_h1 20:00`.

## Результат
`out/initial_plan.json`, `out/improved_plan.json`, `out/recovery_plan.json`, `out/report.html`.

## Что реализовано в протоколе
* Этап 1: груз → CFP всем вагонам → вагон опрашивает ВСЕ локомотивы станции отправления и берёт самый ранний старт → временная блокировка интервала (отказ `BLOCKED` → груз повторяет запрос) → бронь → окна станций → отчёт координатору.
* Вагон учитывает: совместимость и вес, очистку при смене класса груза, положение (предыдущий рейс или домашняя станция), время и стоимость порожнего пробега.
* Окна станций: при занятом окне станция предлагает альтернативу (погрузка – раньше, приём – позже), груз сам её берёт.
* Этап 2: опаздывающий груз сам опрашивает ВСЕ грузы; обмен рейсами внутри вагона и между разными вагонами (двухфазное подтверждение, блокировка броней, атомарная смена тяги, обмен окон станций). Обмен делается, только если улучшение больше ε (`settings.epsilon`) – так «откат» невыгодного улучшения решают сами агенты, а не координатор.
* Отказ вагона (из `input.json` или консолью `fail <вагон> <ЧЧ:ММ>`): отмена броней и незавершённых обменов, уведомление грузов и координатора, замена по очереди срочности, запасной вариант «ждать ремонта», возврат вагона в строй через `settings.repairAfterMs`.

## Известные ограничения
1. Обмен рейсами между вагонами – только при одном локомотиве у обоих рейсов и одинаковом маршруте.
2. Если отказ вагона совпал по времени с применением обмена у локомотива, в расписании локомотива может остаться «осиротевшая» бронь (крайне редкий случай).
3. Штраф при оценке обмена грузы считают по ставке из `costs`; итоговую стоимость всегда подтверждает вагон.
4. Вагон после рейса считается вернувшимся на станцию отправления (оборот включает возврат).

Логика протокола проверена на эмуляторе API JADE (один/два вагона, обмен внутри и между вагонами, конфликт окон, два локомотива, далёкий вагон, отказ и ремонт). На настоящем JADE проект не запускался.
